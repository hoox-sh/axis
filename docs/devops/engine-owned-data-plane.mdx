# Engine-owned data plane

## Goal

Today AXIS is the data owner: the browser loads bars, stores datasets locally,
and sends the bars with every `run`. The target shifts ownership of market data
to the engine when the engine can own it (PYNE Pro):

- **Bar-close / other engines** keep the current bars-in path.
- **PYNE Pro + every tick**: AXIS sends only the script, inputs, and market
  identity (`exchange`, `market`, `symbol`, `interval`, `history_bars`). PYNE
  Pro's persistent store and CCXT feed own the bars. Pro's feed drives both the
  chart and the calculation, so candles and indicators stay aligned.
- **Cache misses** are brokered by AXIS: if the local Data Manager has a
  matching dataset it is uploaded to Pro (auto-upload, decided); otherwise Pro
  fetches from the exchange itself.
- **No local persistence** of streamed bars in this mode. The Data Manager keeps
  metadata only; in-memory chart buffers may still render.

## Decisions

| # | Decision |
|---|----------|
| D1 | Pro's feed supplies both chart bars and script execution in server-owned mode. |
| D2 | On a Pro cache miss, AXIS automatically uploads the matching local Data Manager dataset (if any), else asks Pro to fetch. |
| D3 | Capabilities come from the endpoint's `/health` `features`, never from the engine id. Missing features ⇒ bar-close only. |
| D4 | Pyodide moves to a dedicated Web Worker; live runs coalesce (newest-wins, one in flight). |

## Engine capabilities (`GET /health` → `features`)

PYNE Pro reports these snake_case keys (matches existing `features.*` keys):

```json
"features": {
  "live_modes": ["every-tick", "bar-close"],
  "data_session": true,
  "data_exchanges": ["binance", "bybit", "okx"],
  "live_stream": true
}
```

- `live_modes` absent ⇒ `["bar-close"]`.
- `data_session` absent or false ⇒ `ownsData = false`, no every-tick.
- `data_exchanges` optional, informational.
- `live_stream` (strictly opt-in) ⇒ the engine serves the push subscription
  plane (`WS /ws/live`: `subscribe → status → full → delta → close`, per-subscription
  `seq`, `closed_upto` watermark). Absent ⇒ calculator profile: the legacy
  REST poll paths below stay in service for old backends.

pyne-worker and Pyodide report no such keys and are bar-close only.

## Data store (PYNE Pro)

Persistent OHLCV store, SQLite under `PYNE_DATA_DIR` (default `data/`).

Series key (canonical):

| Field | Canonical form |
|-------|----------------|
| `exchange` | lowercase CCXT id (`binance`) |
| `market` | `spot` (default), `swap`, `future` |
| `symbol` | uppercase, pair form when available (`BTC/USDT`) |
| `interval` | AXIS interval code (`1m`, `5m`, `1h`, `1d`, …) |

Rows: `time` (unix seconds, primary key with the series key), `open`, `high`,
`low`, `close`, `volume`. Upsert by `time` (later write wins for the forming
bar).

## Endpoints (PYNE Pro)

All responses use the existing `{status, code?, message?}` error shape. Auth
follows the existing API-key middleware.

### `GET /data/series`

Query: `exchange`, `market?`, `symbol`, `interval`.

```json
{ "status": "success", "key": "binance|spot|BTC/USDT|1h",
  "count": 5000, "oldest": 1700000000, "newest": 1760000000,
  "updated_at": 1760000100 }
```

Count `0` (and null bounds) when the series is unknown.

### `POST /data/series/provide`

Body: series key fields + `bars: [{time, open, high, low, close, volume}]` +
`source` (e.g. `"axis-local"`). Max 5,000 bars per request; AXIS chunks.

Response: `{status, key, added, updated, count, newest}`.

### `POST /data/series/fetch`

Body: series key fields + `history_bars` (default 5000, max 100000). Pro walks
back through CCXT `fetch_ohlcv` pages and persists the result.

Response: `{status, key, fetched, count, oldest, newest}`. Upstream failure ⇒
`502` with `code: "UPSTREAM"`.

### `GET /data/series/bars`

Query: series key fields + `limit` (default 10000, max 100000). Returns the
newest window for chart paint in server-owned mode. AXIS holds the result in
memory only and never writes it to IndexedDB or localStorage.

```json
{ "status": "success", "key": "...", "count": 500, "bars": [ ... ] }
```

### `POST /data/session`

Body: series key fields + `history_bars` + `script` + optional `inputs`,
`libraries`, `profiler`, `symbol` (display name).

- **Hit** (`count >= history_bars`): `200`, the same envelope as
  `POST /session` plus `session_id`, `cache: "hit"`, and
  `data: {key, count, newest}`. The session is bound to the series key.
- **Miss**: `409`, `{status: "miss", code: "DATA_MISS", key, have, need}`.
  AXIS then runs `provide` (if it holds local bars) or `fetch`, and retries.

### `POST /data/session/{id}/tick`

Body: `{exchange, symbol}` only (AXIS sends identity, never bars). Must match
the session's bound key, else `409 SESSION_KEY_MISMATCH`.

Pro fetches candles since the stored `newest` (with a small overlap), persists
closed bars, re-ticks the forming bar via `update_last_bar`, and appends closed
bars via `append_bars`.

Response: the session envelope plus `appended` (count of newly closed bars),
`forming` (bool), `unchanged` (bool, true when nothing new arrived).

Upstream failure: `502 UPSTREAM`; the session is kept.

### `DELETE /session/{id}`

Existing release route. Unchanged.

## AXIS broker (calculator profile — engines without `live_stream`)

`src/engines/data-sessions.ts` (client + broker):

1. `createDataSession()` → on `hit` return the session id.
2. On `miss`: look up the local Data Manager dataset for
   `(sourceId = exchange, symbol, interval)` via `getDataset` from
   `src/data/dataset-store.ts`.
   - Local bars exist ⇒ `provideDataSeries()` (chunked, last `history_bars`) ⇒ retry create.
   - No local bars ⇒ `fetchDataSeries()` ⇒ retry create.
   - At most two retries, then surface the error.
3. `tickDataSession()` sends `{exchange, symbol}` only.

Chart paint in server-owned mode uses `getDataSeriesBars()` into memory. The
streaming multiplex and `expand-cache` writes are suppressed for that instrument.

## Series staleness (frozen engine series)

`DATA_MISS` is a **count** check: `have < need`. A series that is deep enough but
**frozen** — Pro's upstream feed stopped advancing, or a stale local window was
uploaded before the Data Manager repaired it — never misses, and AXIS paints the
chart from it in engine-owned mode. The chart then freezes at the stale tail on
every tick with no error. Two days of that is the observed live symptom
(`newest` four days back on a 1m series).

The freshness contract is therefore explicit:

- **Pure predicates** (`src/engines/series-freshness.ts`): a series is stale when
  its newest bar lags the reference (chart tail, venue trigger clock, or `now`)
  by more than `ENGINE_SERIES_STALE_STEPS` (2) whole interval steps. Unknown
  bounds are never treated as behind by the *skip* predicates — a wrong skip
  would trade visible staleness for hidden staleness.
- **`GET /data/series` `newest`** is the engine's own series tail and the
  authoritative freshness read (advisory: a failed status read still repairs).
  `tick`'s `unchanged: true` is **not** proof of freshness — a frozen series
  reports unchanged forever.
- **Provisioning top-up** (`sharedProvisionSeries`): after an upload whose tail is
  already stale, Pro is asked to `fetch` so a stale local window can never become
  the engine's frozen tail.
- **Repair** (`repairStaleEngineSeries`, `src/engines/data-sessions.ts`):
  local-first (upload the local window when it reaches now, upsert-by-time keeps
  Pro's deeper history), else `fetch` from Pro's exchange feed. Cooldown-guarded
  (`SERIES_REPAIR_COOLDOWN_MS`, 60s per endpoint+series), never throws.
- **Paint guards**: both engine-owned paint paths refuse to back-date the chart.
  `streams/multiplex.ts` (`paintEngineOwned`, calculator profile) and
  `streams/stream-live.ts` (stream profile snapshots/deltas) keep the fresher
  chart window, report once via `noteStaleEngineSeries` (throttled log +
  `engine` telemetry `degraded` + feed `degraded`), and repair in the background;
  the next snapshot/tick paints the healed window. A **behind-the-venue-clock**
  verdict is a report/repair signal only — the snapshot is still painted when it
  does not back-date the chart (it advances it, or is a no-op); refusing it would
  pin the candles while every other series keeps moving. In the stream plane a
  delta that does not continue the chart tail is dropped (the next full snapshot
  reconciles) instead of punching a hole.
- **Moved-window prune** (`PaneManager.notePaintedCandleRange`): a cookie-cutter
  risk of the repair above is that a *jump* in the candle window (200+ bars,
  e.g. a four-day-frozen series repaired at load) orphans co-painted script
  series — their rows now sit outside the candles. LWC's shared time scale is the
  union of every series' rows, so those rows make the candlestick painter throw
  `Value is null` on every render until the next overlay apply re-clamps them
  (which can be skipped as a no-op). The paint therefore prunes `overlay_*` /
  `bgcolor_*` / equity rows to the new range immediately, in the same task as the
  candle `setData`, before LWC's next render. Compare / on-chain overlay series
  are left alone — their windows are legitimately independent.
- **Background catch-up** (`src/data/background-catchup.ts`): in engine-owned
  mode it skips the local `setBarsQuiet`/`setDataToChart` repaint (the next
  engine snapshot would just hand the stale window back) and pushes AXIS'
  freshest window onto the engine's series instead. This covers the stream plane
  too: an engine advertising both `data_session` and `live_stream` still owns the
  series the subscription replicates, so the same repair-not-repaint rule
  applies.

## Stream plane (engines with `live_stream`)

`src/engine/` + `src/streams/stream-live.ts`, specified in
`.opencode/plans/final/plan.mdx`:

- One WS per engine (`WS /ws/live`, `WS /api/ws/live` via the Worker proxy);
  N subscriptions multiplexed.
- `subscribe` ensures history server-side (autonomous fetch to the last closed
  bar), then `status(datafeed-ready)` → `status(calculating)` → one `full`
  snapshot → `status(live)`; per-tick `delta` + `close` frames with monotonic
  `seq` and the `closed_upto` watermark.
- The client applies snapshots/deltas through the existing apply pipeline
  (`precomputedResult`, tip-only on ticks), re-verifies closed bars against the
  venue, and repairs from the exchange on mismatch.
- Any stream failure falls back to the legacy paths above; a 60s cooldown
  keeps a flapping backend from stalling live. Opt out per tab via
  `axis.engine.stream.disabled`.

## Migration steps

1. **Capabilities** (done in round one, keys aligned to this contract in round two).
2. **PYNE store + routes + health features** (`/home/jango/Git/pynescript`).
3. **AXIS client + broker** (`src/engines/data-sessions.ts`), with unit tests.
4. **Server-owned routing** (done): `serverEngine` takes a `dataSession` option when
   `every-tick` is active and the engine reports `data_session`; the runner
   passes it with identity only, and the chart paints from
   `GET /data/series/bars`.
5. **No-persist in server-owned mode** (done): `isEngineOwnedLive()` in
   `src/engines/ownership.ts` gates both write paths — the multiplex's
   `noteDataManagerLiveBar` and `expand-cache`'s fetch/merge. Fail-open:
   while capabilities resolve, persistence works as before.
6. **Pyodide in a Web Worker** (done): `src/workers/pyodide.*` runs evaluation off the main thread; cancel terminates and respawns the worker. Live-run coalescing is provided by the existing run-epoch + debounce mechanism (newest-wins; stale completions get `meta.superseded` and never touch the chart) — covered by `tests/runner-hardening.test.ts`, so no separate scheduler is needed.
7. **E2E**: the data-session path is covered cross-repo
   (`tests/integration/pyne-data-session.e2e.test.ts` against the real PYNE
   `/data/*` store). A full UI-level e2e (every-tick on Pro without local bars,
   cache-miss upload, bar-close fallback) still needs a browser run.
